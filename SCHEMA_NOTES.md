# Schema Notes — Draft Player Pages

Discovery performed for the `/Draft/<sprocket_id>` player profile page and `/Draft` index page.

## Connector

- Type: **DuckDB** (`@evidence-dev/duckdb`), configured in `sources/sprocket/connection.yaml` with `filename: ":memory:"`.
- There is no Postgres/MySQL database despite those connector plugins being listed in `evidence.config.yaml` — they are unused.
- Every source query in `sources/sprocket/*.sql` is a `SELECT * FROM read_parquet('https://sprocket-public-datasets.nyc3.cdn.digitaloceanspaces.com/datasets/<file>.parquet')` (one exception: `champions.sql` reads a published Google Sheet as CSV). These parquet files are Sprocket's public data exports and are re-downloaded into in-memory DuckDB tables on each dev/build run.
- Column names/types below were initially read from the cached schema files under `.evidence/template/static/data/sprocket/<source>/<source>.schema.json`, then corrected against the real data after running `npm run sources` and querying the freshly-downloaded local parquet files directly — the cached files turned out to be stale for at least one table (see Gaps).

## Current season

`S19_stats` / `S19_standings` / `s19_rounds` exist and are populated (pulled into `main` as part of recent commits — S19 leaderboard/playoffs work). Season 19 is current. Section 5 of the Draft page queries these directly.

## MLEID vs sprocket_id vs member_id

- The `players` table carries **both** `sprocket_player_id` and `member_id` for every player row, so it acts as the bridge table between the two ID systems.
- Every stats table besides `players`/`total_scrim_stats`/`avgScrimStats`/`eligibility` is keyed on `member_id`, not `sprocket_player_id` (e.g. `player_stats`, `S19_stats`, `role_usages`).
- The existing per-player page (`pages/players/[member_id].md`) already uses `member_id` as its canonical site-wide player identifier/URL param, and refers to it informally as the site's player ID. There is no column literally named `mleid` on `players` — the closest literal `mleid` column lives on the unrelated `trackers` table (`trackers.sql`), which separately also has a `"MLE Player ID"` column. I did not join `trackers` against `players` to confirm `trackers.mleid` and `players.member_id` carry the same value for a given player, but every other page in the codebase treats `member_id` as the "MLEID"-equivalent primary key, so the new Draft page header displays `players.member_id` under the label **MLEID**.
- Per Phase 4 of the task: `sprocket_player_id` is present, non-null, and unique on `players` (Sprocket's own internal player ID), so the page stayed on **`sprocket_id`** as the URL param, resolving to `member_id` internally (via `players`) wherever a stats table needs it — mirroring how `pages/players/[member_id].md`'s `scrimStats` query already bridges in the opposite direction.

## Gaps

- **No draft records table exists anywhere in `sources/`.** There is no season/round/pick-number/drafting-franchise dataset — not a missing column on an existing table, but no table at all (checked every `.sql` file under `sources/sprocket/`, `Create All Sprocket Datasets.sql`, and the `archive/` folder for a prior mockup; found none). The "Draft pick" field on the header therefore always renders **"Undrafted"** with a `<!-- TODO -->` comment in `pages/Draft/[sprocket_id].md` marking where a real `draft_picks` (or similar) source query should be joined in once one exists.
- **No dedicated team/roster-history table.** There's no table that records "player X was on team Y specifically for season Z" as a roster assignment — Section 1 (Team History) is derived from `player_stats`, which is a *stats aggregation* table (one row per member_id + season + team_name + gamemode + skill_group whenever the player recorded stats for that team that season). This is a reasonable proxy (confirmed as the existing site's own approach — see "Past Season Stats" in `pages/players/[member_id].md`) but it means a player who was rostered but never played would not show up in Team History.
- **`season` is stored as a free-text string**, not an integer, on both `player_stats` and `S19_stats`. Sort order in Team History uses `REGEXP_REPLACE(season, '[^0-9]', '', 'g')::INT DESC` to sort numerically regardless of exact formatting (e.g. `"19"` vs `"Season 19"`), since the exact string format could not be confirmed without a live query.
- **No `salary rating`/skill-rating-per-game column under that literal name anywhere.** For scrims, the closest analog is `avg_sprocket_rating` (per-scrim average "Sprocket Rating") on `total_scrim_stats`, used as a rounds-weighted average for Sections 3/4's "AVG SR". For Season 19 league play (Section 5), `S19_stats` has no `sprocket_rating` column at all — the closest analog is `gpi`, which `pages/players/[member_id].md` already treats as "Sprocket Rating" (see its Dropdown: `<DropdownOption value=avg_gpi valueLabel="Sprocket Rating" />`), so Section 5's "AVG SR" is `AVG(gpi)`.
- **`total_scrim_stats.gamemode` uses different literals than every other table.** `avgScrimStats`, `S19_stats`, and `player_stats` all use `'RL_DOUBLES'`/`'RL_STANDARD'`, but `total_scrim_stats` uses `'2s'`/`'3s'` — confirmed by querying the real data directly (`SELECT DISTINCT gamemode`). Sections 2–4 (which all read `total_scrim_stats`) map on `'2s'`/`'3s'`; Sections 1 and 5 (which read `player_stats`/`S19_stats`) map on `'RL_DOUBLES'`/`'RL_STANDARD'`. Mapping this wrong is a silent bug, not an error — the query still runs, it just returns all zeros (found by comparing real output across sections for the same player, not from a build failure).
- **`players.sprocket_player_id` is stored as a float upstream** (e.g. `2.0`), so both `player_link` and `profile_url` in `pages/Draft/index.md` `CAST(... AS INTEGER)` it before concatenating into a URL — otherwise every link renders as `/Draft/2.0` instead of `/Draft/2` and 404s against the `[sprocket_id].md` route. `pages/players/non_rostered_players.md` already works around the equivalent issue for `member_id` the same way.
- **The cached `.evidence/.../S19_stats.schema.json` left over from a previous run was stale** and did not match the actual `player_stats_s19.parquet` schema — it described a season-aggregated shape (`season`, `games_played`, `total_goals`, `sprocket_rating`, etc.) that doesn't exist upstream any more. Running `npm run sources` (see Phase 5 below) re-fetched the real, current schema — round-level rows, no `season`/`total_*`/`sprocket_rating` columns — which is what Section 5's query is actually written against. This was only caught by running a real build against live data; the cached schema files from Phase 1 static discovery should be treated as a starting point, not ground truth, for any table you haven't cross-checked against a working existing query.
- **`total_scrim_stats` (`Total_Scrim_Stats_13m.parquet`) only holds a rolling ~13 months of scrim history**, not true career-since-inception data. Sections 2/3 ("Career Scrim Stats") are therefore actually "last 13 months of scrim data" in practice — there is no longer-lived raw scrim log in `sources/`. Labeled as "Career" per spec, but noting the real ceiling here.
- A raw `duckdb` Node binding crashed outright on a remote `read_parquet()` call in this sandbox (reproduced twice, including with `PRAGMA threads=1`), even though plain HTTPS access to the CDN works fine (`curl` succeeds). However, `npm run sources` (the actual Evidence CLI) fetched all 24 datasets successfully, so this was specific to how the ad-hoc probe script invoked DuckDB, not a real sandbox network limitation — `npm run dev`/`build` work as expected. Confirmed with real data afterward: `season` is formatted as `"Season 19"` / `"Season 19 Playoffs"` etc. (validates the digit-extraction sort in Team History), and `sprocket_player_id`/`member_id` are both populated and distinct per player on `players` (e.g. `BigQ`: sprocket_player_id 49 / member_id 50).
